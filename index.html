Capabilities

Transfer engine

How bytes move, and how many connections it takes to move them.

  • Parallel byte-range downloadsLarge files are split into ranges fetched on separate connections, each writing directly at its own offset in the target file.
  • Range plan re-divided while runningA connection that finishes early takes on more work. When there is nothing left to claim, the largest remaining tail is halved and handed to an idle connection. This applies only above 1 MB of remaining tail.
  • Streaming, not bufferingResponses are read through an 80 KiB buffer and written as they arrive, so a 20 GB file is never held in memory.
  • Single write per fileThe target file is created at full length up front and each connection seeks to its own offset, so no temporary parts or second copy exist.
  • Concurrency and bandwidth controlsUp to 3 downloads at once by default, 8 connections per file, and a global speed ceiling in KB/s.

Reliability and integrity

What happens when the network, the server or the power fails.

  • Resume from the last completed rangePer-range progress is flushed to a state file beside the download every two seconds. Reopen after a crash or reboot and it continues.
  • Resume validates before it trustsETag or Last-Modified is sent as If-Range, and only a 206 whose Content-Range starts exactly where it asked is accepted.
  • Changed files are restarted, not splicedIf the file on the server no longer matches, the partial data is discarded and the download starts again rather than producing a file that looks finished and is not.
  • Retry per range, not per fileFive attempts per range with a widening backoff of 2s, 5s, 10s, 20s and 30s. Losing one connection out of eight costs that range and nothing else.
  • Stall detectionA connection that receives no bytes for 30 seconds is treated as dead and its range is retried, because the request timeout does not cover the response body.

Control and queue

Running the queue around your day rather than around the server.

  • Scheduled daily windowSet a start and stop time. The application resumes paused and pending downloads when it opens and pauses active ones when it closes.
  • Bandwidth ceilingOne number in KB/s, enforced across every connection of every download. Zero means unlimited.
  • Authenticated HTTP proxyProxy address, username and password applied consistently to the initial metadata request and every range transfer.
  • Queue actions where you expect themPause, resume, cancel and remove from the toolbar, the right-click menu or the keyboard. Clear completed items in one action.
  • Per-download detail windowSize, bytes transferred, live rate, estimated time remaining, and a bar showing the start position and progress of every individual connection.

Output and safety

What the application does once the last byte lands.

  • Windows Defender scan on completionThe finished file is passed to the Defender scanner already installed on the machine. Best-effort, non-blocking, and never stalls the queue.
  • Automatic file categorisationCompleted files are sorted into folders by detected type, and each queue entry is tagged with its category.
  • Filename from the serverContent-Disposition is honoured where the server sends it, so a download is not saved as a random path segment.
  • Server-side encoding left aloneContent-Encoding is deliberately not decoded, so the bytes written to disk are the bytes the origin sent.
  • Uninstall asks firstYour queue, settings and licence key live outside the install folder. The uninstaller asks before removing them, so reinstalling never silently discards your licence.

Licensing

How entitlement is proved, and what it is bound to.

  • Signed keys, not server lookupsKeys are ECDSA (P-256) signed. Only the public half is compiled into the application, so it can verify a key and can never mint one.

  • Survives a Windows reinstallBecause the binding is to hardware rather than to an operating system install or an account.

Engineering

The actual numbers, not a speed multiplier

Marketing pages usually quote a speed-up factor. Here are the real limits in the shipping build: the mechanism, and its ceiling.

  1. Negotiate

    A HEAD request reads the file size and checks for range support; if the server will not answer HEAD usefully, a one-byte range request is used to read the total from Content-Range instead. That answer decides whether the file can be split at all.

  2. Plan

    The file is divided into ranges sized to your settings and core count. The plan is written to disk immediately and rewritten as it changes, so an unplanned shutdown costs nothing.

  3. Transfer

    Each range runs on its own connection into its own offset, bounded by the concurrency and speed settings, with progress flushed every two seconds. Finished connections claim more work; an exhausted plan hands its largest remaining tail to an idle connection.

  4. Verify and file

    Every range is checked against the length the server declared, so a short or mismatched response is retried rather than accepted. On the last byte, the file goes to Windows Defender and then into its category folder.

Will multi-connection downloading really make my download faster?

Sometimes, and it depends on three things you control only partly. When the origin advertises HTTP range support, a single connection is often limited by latency and by per-connection shaping, so splitting a large file across several byte ranges uses more of the available bandwidth. The gain is largest on large files over connections that shape per stream. On small files, on a link that is already saturated, or against a server without range support, there is little or nothing to gain.

LaPanda IDM probes for range support before it starts and shows you what it found, so you can tell which of those cases you are in. It will not tell you a file is accelerated when it is not.

Does it genuinely resume, or does it quietly start over?

It resumes. Progress for each byte range is written to a small state file beside the download every two seconds, so a crash, a power cut or a reboot costs you seconds of work rather than the whole file.

It also checks before it trusts. Resume sends the ETag or Last-Modified of the file it started on as If-Range, and only accepts a 206 response whose Content-Range begins exactly where it asked. If the file on the server has been replaced, the partial data is thrown away and the download restarts, rather than appending two different versions into a file that looks finished and is not.

Why does every download show a different number of connections?

Because the decision is made per file, from what the server actually said. Files below about 256 KB, and any file from a server that does not advertise range support, are fetched on a single connection because splitting them would not help. Above that, connections are capped at twice your logical processor count, so on a four-core machine the maximum is 8 no matter what the setting says.
